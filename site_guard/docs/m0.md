# M0: design, implementation, and validation

## Scope

M0 establishes the smallest useful access-phase policy module without changing
Nginx core code. It provides deterministic request filtering and a safe test
baseline before introducing shared mutable state.

Included:

- main GET and HEAD request handling;
- inherited `http`, `server`, and `location` configuration;
- exact full-Referer rules with an optional trailing slash;
- normalized-URI exclusion prefixes;
- shadow and enforce modes;
- configurable 400-599 response status;
- `$site_guard_status` for access-log validation.

Explicitly deferred:

- runtime rule replacement;
- shared-memory counters and cross-IP aggregation;
- external management APIs, regular expressions, and challenges.

## Design decisions

### Independent addon

The module is built with `--add-module=./site_guard`. No Nginx core file is
changed, which keeps upgrades and review focused on one directory.

### Access phase

`ngx_http_site_guard_init()` appends the handler to
`NGX_HTTP_ACCESS_PHASE`. Matching therefore runs before static content handling
and can terminate an enforce-mode request without reading the requested file.

### Configuration ownership

Each location owns its configuration. Arrays and scalar values inherit from the
parent only when the child has not supplied them. Status values are validated
at configuration merge time.

### Request identity and matching

Only the main request is evaluated. Exclusions use `r->uri`, which is Nginx's
normalized URI rather than the raw request target. M0 compares the complete
Referer value, avoiding substring host matches. One trailing slash is ignored
on either side.

### Observability

The request context records the outcome for `$site_guard_status`:

- `PASSED`: enabled, but no rule matched;
- `MATCHED`: enforce-mode match;
- `MATCHED_DRY_RUN`: shadow-mode match;
- `DISABLED`: module disabled for the request.

A notice log is emitted for each match. This is adequate for an isolated M0 but
requires sampling or rate limiting before high-volume production use.

## Validation environment

- Source baseline: official `release-1.30.4`;
- Module revision: `16e8eb0`;
- Build directory: `/data/build/nginx-site-guard`;
- Test prefix: `/data/build/site-guard-test`;
- Test listener: loopback TCP port 18089;
- Build: `nice -n 19 make -j1`;
- No install step and no production process reload.

The resulting `objs/nginx` passed `nginx -t` with the private prefix. The online
master process and its configuration were not replaced.

## Results

| Case | Expected | Observed |
|---|---:|---:|
| Excluded `/nn/` URI with matching Referer | 200 / PASSED | 200 / PASSED |
| Matching Referer outside exclusion | 403 / MATCHED | 403 / MATCHED |
| Matching Referer with trailing slash | 403 / MATCHED | 403 / MATCHED |
| Unmatched Referer | 200 / PASSED | 200 / PASSED |
| Missing Referer | 200 / PASSED | 200 / PASSED |
| Shadow-mode match | 200 / MATCHED_DRY_RUN | 200 / MATCHED_DRY_RUN |

Representative access-log output:

```text
200 PASSED
403 MATCHED
403 MATCHED
200 PASSED
200 PASSED
200 MATCHED_DRY_RUN
```

The shadow-mode error log included `dry run`. The isolated instance was stopped
after testing, and the public site returned HTTP 200 with the original master
process still running.

## Exit assessment

M0 meets its purpose: the addon builds against the target release, deterministic
rules execute in the access phase, shadow mode is non-blocking, and enforce mode
changes only the isolated test instance. M1 can add runtime state without
revalidating the basic policy model from scratch.
